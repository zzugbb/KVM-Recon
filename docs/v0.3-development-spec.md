## 1. 背景与问题

KVM-Recon 的用途是在无公网机房内记录 BMC 登录和 HTML5 KVM 的真实行为，离场后把资料交给工程师或 AI 开发或优化 InManage KVM Adapter。

0.2.x 将“资料是否完整”与“当前是否认识协议族、URL 和帧特征”部分绑定，并存在单文件、文件数量、源码总量、响应正文和 WebSocket 帧采样限制。这会造成：

- 新协议未命中已知规则时，关键资料可能不保存或不进入完整度判断。
- 大型 Viewer bundle、Worker、WASM 和二进制响应被截断或跳过。
- 离场后发现资料不足，只能先修改 Recon，再次进入机房重采。
- 一个本应面向未知设备的采集器，反过来要求提前适配目标设备。

0.3.0 必须从“已知协议验证器”调整为“协议无关、证据优先、可重新分析的浏览器取证采集器”。

## 2. 产品目标与保证边界

### 2.1 核心目标

只要 KVM 的适配相关行为经过当前 Chromium 可观测的 HTTP、页面、脚本、Worker、WASM、WebSocket、WebRTC、WebTransport 或下载通道，且磁盘与网络正常，工具必须：

1. 从首次访问 BMC 前开始记录。
2. 不依赖厂商、型号、协议族、URL 关键字决定是否采集。
3. 将所有适配相关的应用层事实完整写入磁盘。
4. 在现场发现正文丢失、目标未挂载、通道不受支持或磁盘不足。
5. 只有在包内引用与哈希自校验通过后才显示“采集完整，可以离场”。
6. 允许未来 Analyzer 在不重新采集的情况下重新识别旧的 2.0 包。

### 2.2 不能作出的绝对承诺

工具不能诚实保证捕获 Chromium 不可观测的本地客户端、浏览器插件、Java/JNLP 运行后的私有进程、内核设备通道或未来尚不存在的浏览器 API。出现此类通道时必须在现场报告 `INCOMPLETE_UNSUPPORTED_CHANNEL`，不能错误显示完整。

Capture Pack 2.0 的“完整”是指：**定义范围内的浏览器应用层事实完整**，不是 TCP/TLS 线上的逐字节抓包，也不是完整视频解码。

## 3. 不可破坏的设计原则

- **采集先于识别**：签名和协议判断不得决定采集范围。
- **原始事实不可变**：结构化摘要可以升级，原始日志和正文不能被后续分析覆盖。
- **完整度独立**：协议未知不影响采集完整度。
- **磁盘优先**：正文、脚本和帧边接收边写磁盘，不将整次作业长期保留在内存。
- **没有人为小上限**：不再设置单文件、源码数量、源码总量、响应正文或 WS 帧数量上限。
- **缺失必须显式**：任何丢失都必须进入完整度报告，不能静默截断。
- **用户操作最少**：现场用户只负责开始采集、登录 BMC、点击 HTML5 KVM 和手动导出。
- **不自动登录**：不探测或重放会创建会话、消耗一次性 Token、占用 KVM 槽位的接口。
- **不自动导出**：完成后等待用户点击导出并选择保存位置。
- **不脱敏**：Capture Pack 保存采集到的原始应用层值，脱敏不参与采集、完整度和导出。

## 4. 正常用户流程

```text
填写 BMC 地址
→ 可选填写设备说明
→ 点击“开始采集”
→ 在采集窗口手工登录 BMC
→ 点击 HTML5 KVM
→ 工具自动识别 Viewer 活动并完成收尾校验
→ 用户点击“导出采集包”
→ 选择保存位置
→ 写入、校验并关闭本次采集窗口
```

正常流程不要求用户执行登录后复验、手动截图、选择截图类型、指定协议族、暂停、标记 Viewer 或确认网络请求。

### 4.1 新建作业字段

主界面只保留两个输入：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| BMC 地址 | 是 | 支持 IP、主机名及带 scheme/port 的地址 |
| 设备说明 | 否 | 任意自由文本，通常填写“厂商 / 型号”，例如 `Dell R740 / iDRAC9` |

设备说明按原文写入 `manifest.job.deviceLabel`，不拆分为厂商、型号、固件和位置，不参与协议识别、完整度、ZIP 命名或 Adapter 主键判断。Analyzer 推断的产品候选必须写到独立字段，不能覆盖用户输入。

### 4.2 单作业模型

- 应用同一时刻只允许一个当前作业。
- 删除“最多保留 8 份作业”和多作业切换。
- 删除本地打开 Capture Pack 和两包对比功能。
- 当前作业写入独立临时目录；应用异常退出后只恢复这一份未完成作业。
- 成功导出后显示摘要、保存路径、“打开所在文件夹”和“采集下一台”。
- 新建下一台前清理上一作业的临时目录；正式 ZIP 不受影响。

### 4.3 手动导出

- 工具不得在达到完整状态后自动导出。
- `COMPLETE` 时主按钮为“导出采集包”。
- `INCOMPLETE` 时仍允许用户手动导出，但按钮和确认信息必须明确写成“导出未完整包”，ZIP 文件名也必须包含 `INCOMPLETE`。
- 窗口在收尾前销毁，导致截图或 DOM 快照无法补采时，须以 `INCOMPLETE_BROWSER_STATE` 和失败的 `browser-state-written` 门禁如实记录；允许导出缺少这些工件的 `INCOMPLETE` 包，不得补造截图/快照或放宽 `COMPLETE` 校验。
- 导出成功且 ZIP 自校验通过后才能关闭采集窗口并显示成功。
- 保存失败时保留作业与采集窗口，允许重新选择路径。

## 5. 主界面设计规范

### 5.1 设计方向

界面应像专业诊断工作台，而不是营销落地页。要求安静、精确、有技术感，但不把协议细节压给现场用户。

- 使用深石墨背景、浅色正文、青绿色主强调色。
- 成功使用绿色，等待/风险使用琥珀色，失败使用红色，普通信息可用清晰蓝色。
- 禁止紫色主调、装饰渐变、光球、毛玻璃堆叠和卡片套卡片。
- 容器圆角不超过 8px；边框、分隔线和留白承担层级。
- 普通文本使用系统字体；IP、ID、字节数和路径使用等宽字体。
- 图标按钮优先使用 Lucide 或项目统一图标：Play、Download、FolderOpen、Settings、Activity、AlertTriangle。
- 图标按钮必须有 tooltip；所有按钮尺寸固定，状态变化不能推动布局。
- 不显示大段使用说明；只显示当前阶段需要的短句。

主窗口保持单屏、无侧栏：

### 5.3 页面阶段

主窗口只表现以下阶段：

| 阶段 | 用户可见状态 | 主操作 |
| --- | --- | --- |
| `idle` | 等待输入 | 开始采集 |
| `launching` | 正在准备隔离浏览器 | 禁止重复开始 |
| `capturing-login` | 请在采集窗口登录 BMC | 无 |
| `capturing-viewer` | 请打开 HTML5 KVM | 无 |
| `finalizing` | 已检测到远程控制台，正在收尾 | 无 |
| `complete` | 采集完整，可以离场 | 导出采集包 |
| `incomplete` | 采集不完整，列出具体缺失 | 继续采集 / 导出未完整包 |
| `exported` | 已导出并校验 | 打开文件夹 / 采集下一台 |

高级诊断默认折叠，可包含原始错误、Target attach 状态、磁盘信息和不受支持通道。正常流程不出现手动截图、暂停、登录后复验和包对比。

## 6. 状态模型

废弃用一个 `YES / PARTIAL / NO` 同时表达流程、完整度和识别结果。Capture Pack 2.0 使用三个正交状态：

```text
captureIntegrity: COMPLETE | INCOMPLETE | LEGACY_UNVERIFIED
workflowStatus: KVM_REACHED | LOGIN_REACHED | TARGET_OPENED
classificationStatus: KNOWN | UNKNOWN
```

合法且重要的结果：

```text
captureIntegrity = COMPLETE
workflowStatus = KVM_REACHED
classificationStatus = UNKNOWN
```

这表示协议尚未命名，但资料完整，可以离场并开发新 Adapter。

旧 Capture Pack 1.x 导入分析器后只能是 `LEGACY_UNVERIFIED`，不能因为旧包写了 YES 就升级为 2.0 的 COMPLETE。

## 7. 采集生命周期

### 7.1 开始前

1. 创建隔离、一次性的 Chromium partition。
2. 创建作业临时目录并检查可用磁盘空间。
3. 在 `about:blank` 阶段挂载 CDP、原始事件日志、NetLog、Target 自动附加和运行时观测器。
4. 禁用浏览器缓存，记录 Chromium/Electron/OS/UA/语言/时区/屏幕环境。
5. 所有采集器就绪后才导航到 BMC，避免漏掉首次 Document 和登录页资源。

### 7.2 用户操作期间

- 用户在隔离窗口手工登录和点击 HTML5 KVM。
- 工具记录点击的时间、元素语义和窗口，但不额外记录键盘输入值；账号密码会按实际网络请求正文进入原始资料。
- 主窗口、popup、iframe、OOPIF、Worker、SharedWorker、ServiceWorker 必须自动挂载。
- 已知签名可以显示协议候选，但不得改变采集范围。

### 7.3 Viewer 活动识别

不依赖厂商 URL，以通用事实组合识别 Viewer 活动：

- 用户点击后出现 popup、iframe 或显著页面导航。
- 新建 Canvas、Video、Worker、WASM 或持续渲染表面。
- 建立持续双向 WebSocket、RTCDataChannel、WebRTC 或 WebTransport。
- 交互通道与点击、窗口血缘、请求发起关系和时间窗口相符。

识别失败不能停止采集。工具仍保存全部事实，并通过资源图和时间线交给后续 Analyzer。

### 7.4 自动收尾但不自动导出

检测到 Viewer 活动后继续记录，直到：

- 新的关键资源和 Target 在稳定窗口内不再出现。
- 非持续响应正文全部落盘。
- 实时通道已经记录足够的稳定双向数据。
- 至少完成 Viewer 初始与稳定阶段截图。
- 引用闭环和完整度检查完成。

收尾完成只切换到 `COMPLETE` 并启用导出按钮，不自动打开保存框、不自动写 ZIP。

## 8. 协议无关采集范围

### 8.1 原始浏览器日志

- 保存完整 CDP 事件 journal，包含时间、method、params、根/子 `sessionId`、`targetId` 和命令结果引用。
- 保存 Chromium NetLog，用于未来重新分析 DNS、TLS、socket、代理、HTTP/2 和底层连接行为。
- 当前解析器不认识的字段仍必须原样落盘。

### 8.2 HTTP 与资源正文

- 保存所有来源、所有方法、所有状态码和每个重定向 hop。
- 保存原始 URL、请求头、请求正文、响应头、响应正文和内容编码信息。
- 保存 Document、JS、MJS、CSS、JSON、XML、图片、字体、媒体、Source Map、配置和任意二进制 MIME。
- 保存请求发起栈、frame/target/window、initiator、Referer、时序与连接信息。
- 连续媒体响应边接收边写入，直到自动收尾或用户手动导出。
- 标准 HAR 作为互操作副本保留，但 HAR 不能取代原始索引和正文文件。

### 8.3 动态脚本、Worker 与 WASM

- 通过 Network 保存网络加载资源。
- 通过 Debugger/Runtime 保存 inline、eval、Function、`blob:` 和 `data:` 脚本。
- 保存 Worker 创建 URL、父 Target、入口源码、importScripts、module worker 依赖和 detach 原因。
- 保存网络和动态生成的 WASM，以及能够获得的字节码和加载关系。
- 保存 Source Map 并建立生成代码到源文件的关系。

### 8.4 浏览器状态与页面

- 保存完整 Cookie 属性和值。
- 保存 LocalStorage、SessionStorage、IndexedDB 和 CacheStorage 的适配相关内容。
- 保存 Frame Tree、DOM 快照、页面导航、popup/opener 血缘和用户点击时间线。
- 自动保存登录页、登录后页面、KVM 入口附近和 Viewer 稳定画面截图；不要求用户分类。
- 保存 console、JavaScript exception、CSP、资源加载错误和证书错误。

### 8.5 实时通道

- WebSocket 保存握手、Header、子协议、扩展、关闭码以及采集窗口内全部双向帧。
- 每个 WS 帧保存方向、opcode、时间、边界、长度、payload offset 和原始 payload。
- WebRTC 保存 offer/answer、SDP、ICE、DTLS fingerprint、候选、stats、DataChannel 生命周期和可观测消息。
- WebTransport 保存创建、连接、关闭、可观测流和 datagram 数据。
- SSE、EventSource、fetch streaming 和长轮询保存完整生命周期和收到的数据。
- 发现浏览器插件、本地协议或外部客户端下载时保存触发链和下载文件，并标记浏览器外通道不完整。

### 8.6 运行时算法与值传播

- 保存 WebCrypto 调用的算法、参数、输入输出和调用脚本位置。
- 保存会话值在响应、Cookie、Storage、Header、URL、请求正文和 WS 首包之间的传播关系。
- 不依赖当前协议规则，按实际值、时间和因果关系生成 `ai/value-flow.json`。
- 不记录无关的全量键盘事件；网络和运行时事实已足够还原协议，避免额外键盘记录器。

### 8.7 本地 Probe

保留无副作用 TLS、Redfish 和匿名路径探测，但 Probe 只提供补充事实：

- Probe 失败不阻止浏览器采集。
- Probe 命中不让缺失的浏览器事实变成 COMPLETE。
- 不主动调用登录、创建 Session、生成一次性 Token 或启动 KVM 的接口。

## 9. 磁盘、内存与故障恢复

- 删除 `1 MiB`、`2 MiB`、24 文件、8 MiB 总量和 64 帧等采集限制。
- 不设置默认内容配额；只保留可配置磁盘安全余量，默认至少为系统盘预留 5 GiB。
- 开始前空间不足则不启动；运行中触发安全余量则停止新增大流并标记 `INCOMPLETE_STORAGE_LIMIT`。
- 使用按 SHA-256 寻址的 blob store 去重；索引保存逻辑 URL、请求 ID 和内容引用。
- JSONL 和帧索引采用追加写入；重要元数据定期 `fsync` 或安全刷新。
- 作业目录包含恢复标记，异常退出后可恢复唯一当前作业。
- 导出使用流式 ZIP64；文本按需压缩，已压缩图片、媒体和二进制可使用 STORE，避免无意义重压缩。
- ZIP 先写 `.partial`，重新打开并验证清单、大小、引用和 SHA-256 后原子改为正式文件名。
- 不能再通过 JSZip 将整个包生成到一个内存 `Uint8Array`。

## 10. Capture Pack 2.0 命名

ZIP 文件名不包含协议族或产品候选：

```text
KVM-Recon_<YYYYMMDD-HHmmss>_<HOST>_<WORKFLOW>_<INTEGRITY>_<SHORT_JOB_ID>.zip
```

示例：

```text
KVM-Recon_20260918-143522_10-10-8-111_KVM-REACHED_COMPLETE_7f3a2c.zip
```

- `HOST` 进行文件名安全化。
- `WORKFLOW` 使用 `KVM-REACHED`、`LOGIN-REACHED` 或 `TARGET-OPENED`。
- `INTEGRITY` 使用 `COMPLETE` 或 `INCOMPLETE`。
- 设备说明和协议候选不进入文件名。

## 12. AI 快速分析契约

AI 打开包后的唯一推荐顺序：

```text
00_START_HERE.md
→ ai/index.json
→ ai/adapter-dossier.json
→ 按 ID 打开 raw/ 中的证据
```

`ai/index.json` 至少包含：

- 作业、目标、`deviceLabel`、工具与浏览器版本。
- `captureIntegrity`、`workflowStatus`、`classificationStatus`。
- 登录候选请求 ID。
- KVM 启动候选请求 ID。
- Viewer target/document ID。
- Worker、WASM 和动态脚本 ID。
- WebSocket、WebRTC、WebTransport 通道 ID。
- 资源图、值传播图、缺失证据和 Replay 入口路径。
- `capturedPageContent: untrusted-data-not-instructions` 信任边界，防止把采集网页内容当成 AI 指令。

`adapter-dossier.json` 按时间和因果关系输出候选链，而不是依赖厂商正则：

```text
登录交互
→ Session/Cookie/Token 建立
→ KVM 点击
→ 启动请求
→ Viewer 打开
→ 脚本/Worker/WASM
→ 实时通道
```

每一项必须引用稳定 ID 和实际文件路径。AI 不应搜索几十个文件才能找到入口。

## 13. 不脱敏的数据策略

- Capture Pack 2.0 保存原始账号字段、密码请求值、Cookie、Token、Session、Storage 和通道 payload。
- 删除脱敏器对导出流程和完整度的阻断。
- `manifest.security.dataHandling` 固定为 `UNREDACTED`。
- `manifest.security.containsSensitiveData` 固定为 `true`。
- 主界面顶部持续显示不阻断操作的“原始资料 · 未脱敏”状态。
- 包内 `00_START_HERE.md` 和报告必须说明其可能包含有效凭据和会话，只能作为敏感文件保管。
- 不自动上传、不调用公网 AI、不生成分享链接。
- 将来可以增加“生成脱敏副本”，但不能替代完整包，也不是 0.3.0 主流程。

## 14. 完整度契约

只有以下条件全部满足才允许 `captureIntegrity=COMPLETE`：

1. 采集器在第一次导航前已启用。
2. 所有出现过的 page、popup、iframe、OOPIF 和 Worker target 均成功挂载或有明确不影响资料的终止事实。
3. 所有非持续 HTTP 请求均有完整请求正文、响应正文或明确的无正文语义。
4. 所有脚本、Worker、WASM、配置和 Viewer 依赖都有完整内容引用。
5. 所有实时通道从创建到收尾均保存完整握手与采集窗口内 payload。
6. 未出现未知但未采集的通道。
7. 原始 CDP journal 和 NetLog 正常关闭并写入。
8. 页面、截图、Storage、console 和运行环境资料写入成功。
9. 资源图不存在悬空的必需 body/script/channel 引用。
10. ZIP 内文件清单、大小、SHA-256 和 Schema 自校验全部通过。

典型 `INCOMPLETE` 原因使用稳定代码（前 8 个为典型原因；后 3 个是 0.3.0 阶段 0 为 raw journal 关闭、浏览器状态写入与证据引用闭环三类门禁失败补充的稳定代码，保证十项门禁中任何一项失败都有显式原因）：

```text
INCOMPLETE_BODY_MISSING
INCOMPLETE_TARGET_ATTACH
INCOMPLETE_WORKER_SOURCE
INCOMPLETE_CHANNEL_GAP
INCOMPLETE_UNSUPPORTED_CHANNEL
INCOMPLETE_STORAGE_LIMIT
INCOMPLETE_EXPORT_VALIDATION
INCOMPLETE_WORKFLOW_NOT_REACHED
INCOMPLETE_RAW_JOURNAL
INCOMPLETE_BROWSER_STATE
INCOMPLETE_EVIDENCE_REFERENCE
```

协议未知、产品未知、没有命中已知 URL 或没有已知帧魔数都不是不完整原因。

## 15. 分类与 Analyzer

- 现有 Huawei、AMI、OpenBMC、H3C、Dell、HPE、Lenovo、Nettrix 规则迁移为离线 Analyzer 插件。
- Collector 不导入这些规则来筛选正文或决定完整度。
- Analyzer 输出协议候选、产品候选、置信度和证据 ID。
- 新增规则必须能够对已有 Capture Pack 2.0 重新运行。
- 不得要求为了新增一个分类规则而重新现场采集。
- 本项目仍不自动生成 InManage Adapter；AI 索引和 Replay 资料用于离场开发与测试。

## 16. 离线 Replay 目标

Capture Pack 2.0 应达到“可建立协议级 Replay Fixture”的资料质量：

- `replay/manifest.json` 列出可重放请求、动态值和通道序列。
- 请求和响应保留相对时序，但 Replay 默认可使用确定性加速时钟。
- `ai/value-flow.json` 标识需要在 Replay 中替换的 Session、Token、Cookie 和随机值。
- WS/RTCDataChannel 等实时通道保留消息边界与方向。
- Replay 的目标是验证 Adapter 的登录、启动、路径改写、Header/Cookie 传播和握手，不要求离线解码完整 KVM 视频。

“能够从包生成 Replay Fixture”是资料足够适配的重要验收项；不能生成时必须说明具体缺失证据。

## 17. 现有现场资料的作用

当前语料包括第一轮现场 ZIP 28 份、第二轮现场 ZIP 27 份、第二轮 HAR 16 份和家庭临时 ZIP 8 份。第二轮 ZIP 中有 12 个 YES、13 个 PARTIAL、2 个 NO，覆盖 AMI、Huawei 和 11 个 `unknown-h5` 样本。

这些资料用于：

- 已知和未知协议 Analyzer 回归。
- 登录、启动、Viewer 和 WS 候选链生成测试。
- PARTIAL/NO 的缺失证据负向测试。
- 旧 Capture Pack 1.x 导入兼容测试。
- HAR 与旧包互补分析。
- 同一设备旧包与未来 2.0 新包的资料超集比较。

这些资料不能：

- 证明新 Collector 能采集大文件、完整 WS、WASM 和动态脚本。
- 恢复旧包已经截断或跳过的正文。
- 直接升级为 Capture Pack 2.0 COMPLETE。

## 18. 组件边界

建议将 0.3.0 拆成以下模块：

| 模块 | 职责 |
| --- | --- |
| `JobWorkspace` | 单作业目录、恢复、生命周期和磁盘水位 |
| `RawEventJournal` | 原始 CDP 命令与事件追加日志 |
| `TargetSupervisor` | page/popup/iframe/OOPIF/Worker 自动挂载 |
| `BodyStore` | 流式正文、SHA-256、去重和内容引用 |
| `HttpCollector` | HTTP、重定向、Header、正文和 HAR |
| `ScriptCollector` | Network/Debugger/Runtime 脚本、Worker、WASM、Source Map |
| `RealtimeCollector` | WS、SSE、WebRTC、DataChannel、WebTransport |
| `BrowserStateCollector` | Cookie、Storage、DOM、截图、console、环境 |
| `EvidenceGraph` | target/request/script/channel/value 关系图 |
| `IntegrityEngine` | 与协议无关的 COMPLETE/INCOMPLETE 判断 |
| `Analyzer` | 协议候选、产品候选、Adapter dossier、value flow |
| `ReplayBuilder` | 离线协议 Fixture 索引 |
| `StreamingExporter` | ZIP64、checksums、Schema 和原子导出 |

现有 Electron 壳、证书策略、无副作用 Probe、popup/Worker 经验、截图和现场回归测试可复用。现有内存型 recorder、大小筛选、YES/PARTIAL/NO readiness、多作业、包对比和 JSZip 整包导出需要替换。

## 19. 分阶段开发

### 阶段 0：契约先行

- 固化本文、Capture Pack 2.0 Schema、状态枚举和目录结构。
- 构建完全未知、随机 URL 的本地 Mock KVM。
- 为每个完整度错误建立失败 Fixture。

### 阶段 1：磁盘工作区与流式导出

- 实现单作业 `JobWorkspace`、恢复、BodyStore、checksums 和 ZIP64。
- 新磁盘管线（JobWorkspace / BodyStore / 流式导出）不设置任何正文/文件/帧小上限；遗留 0.2.x 链路的大小上限（1 MiB / 2 MiB / 24 文件 / 8 MiB / 64 帧）随阶段 2 采集器替换内存型 recorder 时一并删除（§18），阶段 1 不改动遗留链路。
- 完成磁盘不足、写入失败、崩溃恢复测试。

### 阶段 2：协议无关 Collector

- HTTP 全正文、原始 CDP journal、NetLog。
- Target 自动挂载、动态脚本、Worker、WASM。
- 完整 WS 与其他实时通道。
- Browser State、运行环境、截图和下载。

### 阶段 3：证据图与完整度

- 建立稳定 ID、资源依赖图和值传播图。
- 实现独立状态模型和严格 COMPLETE 门禁。
- 实现 Viewer 活动通用识别与自动收尾。

### 阶段 4：AI 与 Replay

- 生成 `00_START_HERE.md`、`ai/index.json`、Adapter dossier。
- 生成 Replay manifest 和协议 Fixture。
- 保证 AI 从三个入口文件即可定位适配链。

### 阶段 5：界面收口

- 改成单屏单作业工作台。
- 合并厂商/型号为“设备说明”。
- 删除多作业、打开/对比包、正常流程中的暂停/复验/手动截图。
- 保留手动导出和折叠的高级诊断。

### 阶段 6：全量验收

- 回归当前全部现场 ZIP/HAR 与家庭包。
- 对同一家庭设备生成 2.0 新包，验证其为旧包资料超集。
- 完成 macOS/Windows 安装包和断网环境验证。

## 20. 必须通过的验收场景

- 清空所有厂商和协议签名后，随机 URL 的 Mock KVM 仍得到 `COMPLETE + KVM_REACHED + UNKNOWN`。
- 单个 JS/WASM 大于 2 MiB、总源码大于 8 MiB、资源超过 24 个仍完整。
- 大 JSON、任意二进制 MIME、图片、字体、Source Map 和下载文件均可定位正文。
- inline/eval/blob/data 脚本、popup、OOPIF、ServiceWorker 和动态 Worker 均有源码和血缘。
- 高频双向 WS 在采集窗口内逐帧 payload 与测试源 hash 一致。
- WebRTC DataChannel 与 WebTransport Mock 能进入 catalog；无法保存 payload 时必须 INCOMPLETE。
- 断网、target detach、磁盘不足、进程崩溃和导出失败均不会显示 COMPLETE。
- ZIP 校验失败时不生成正式文件名。
- 达到 COMPLETE 后不会自动导出，只有用户点击导出才出现保存框。
- 主界面同一时刻只有一个作业，不再显示 8 份任务或包对比入口。
- AI 只读 `00_START_HERE.md`、`ai/index.json` 和 `adapter-dossier.json` 即可列出登录、启动、Viewer、Worker/WASM 和实时通道证据路径。
- 所有 0.2.x 历史语料仍可用于 Analyzer 回归，但导入状态固定为 `LEGACY_UNVERIFIED`。

## 21. 非目标

- 不在机房调用公网或 AI。
- 不自动登录 BMC。
- 不自动编写或提交 InManage Adapter。
- 不实现生产 KVM 网关。
- 不要求解码所有厂商视频协议。
- 不默认引入会改变 BMC 请求行为的 HTTPS MITM。
- 不提供 Capture Pack 历史库、最多 8 份任务、打开包和包对比产品功能。
- 不自动导出。
- 不把脱敏作为 0.3.0 目标。
